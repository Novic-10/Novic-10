Executive Summary & Overview

This writeup details the investigation into a Windows Print Services exploit, likely a variant of PrintNightmare, conducted by a red team for a vulnerable setup. As part of the blue team, the objective was to analyze system logs and network captures to identify key artifacts for detection rule creation. The incident involved the deployment of a malicious DLL, the exploitation of the spoolsv.exe process, establishment of a reverse shell, and subsequent post-exploitation activities, including privilege escalation to NT AUTHORITY\SYSTEM. The analysis focused on Sysmon.evtx and Security.evtx logs to trace the attacker's actions and identify indicators of compromise (IOCs).

Execution Chain & MITRE ATT&CK Mapping

Stage 1 — Initial Compromise & DLL Deployment: The red team leveraged a vulnerability in Windows Print Services, likely PrintNightmare, to achieve initial access and deploy a malicious DLL, printevil.dll, to a specific location within the print spooler's driver directory. This action was facilitated by a domain setup redteam.lab.

Stage 2 — Exploit Trigger & Process Execution: The exploit caused the spoolsv.exe process to trigger WerFault.exe, indicating a crash or an attempt to execute arbitrary code within the context of the print spooler service, often a precursor to privilege escalation.

Stage 3 — Command and Control: Following successful exploitation, the attacker established a reverse shell connection to their C2 server at 10.0.2.15:443, providing remote access to the compromised system.

Stage 4 — Discovery & Privilege Escalation: The attacker executed the whoami command, revealing that they had successfully elevated privileges to NT AUTHORITY\SYSTEM, granting full control over the system.

Stage 5 — Network Share Object Access: The attacker, operating under the printuser account, attempted to access the spoolss named pipe via an IPC share, requesting specific permissions (AccessMask 0x3), indicating further interaction with the print spooler service for potential lateral movement or persistence.

Question & Answer Solutions

Let's walk through each investigation question in order, tracing how each artifact and memory or log clue points to the answer.

1. Submit the Domain name used by the red teamers for their test setup

redteam.lab

Reasoning: This was identified by examining Sysmon Event ID 3 (Network Connection). The only log entry revealed the domain name redteam.lab associated with the network activity.

2. What is the C drive location where the file from the previous question is copied?

C:\Windows\System32\spool\drivers\x64\3\New\printevil.dll

Reasoning: By filtering Sysmon Event ID 11 (File Creation), we can observe the creation of the malicious DLL, printevil.dll, at the specified path within the print spooler's driver directory.

3. Submit Parent Command Line for the process WerFault.exe

C:\Windows\System32\spoolsv.exe

Reasoning: Analyzing process creation events (e.g., Sysmon Event ID 1) reveals that WerFault.exe was spawned by spoolsv.exe, indicating a crash or exploit within the print spooler service that triggered the Windows Error Reporting process.

4. What is the attacker's IP:Port for reverse shell?

10.0.2.15:443

Reasoning: Network connection logs (e.g., Sysmon Event ID 3 or packet capture analysis with Wireshark) show an outbound connection from the compromised host to 10.0.2.15 on port 443, which is characteristic of a reverse shell connection.

5. Submit EventID, AccessMask, ShareName when Accountname="printuser", Sourceaddress=Attacker's IP and Relative Target Name is "spoolss"

5145, 0x3, \\*\IPC$

Reasoning: By filtering the Security Event Log for Event ID 5145 (Network Share Object Access) with Accountname="printuser", Sourceaddress=10.0.2.15 (attacker's IP), and Relative Target Name="spoolss", we can pinpoint the specific event showing the requested access mask 0x3 and the share name \\*\IPC$.

6. Submit EventID, AccessMask, ShareName when Accountname="printuser", Sourceaddress=Attacker's IP and Relative Target Name is "spoolss"

C:\Windows\System32\spoolsv.exe

Reasoning: This question appears to be a duplicate of question 5 in its prompt, but the provided answer C:\Windows\System32\spoolsv.exe suggests it's asking for the process associated with the spoolss pipe access. This is the legitimate Windows Print Spooler Service executable, which was the target of the exploit.

7. After getting the reverse shell, the attacker tried the command “whoami”, what will be the output of this command? Note: whoami displays user, group, and privileges information for the user who is currently logged on

nt authority\system

Reasoning: The output of the whoami command, nt authority\system, confirms that the attacker successfully escalated privileges to the highest level on the compromised Windows host after gaining the reverse shell.

Key Takeaways & Security Insights

  • •
    SMB3 Traffic Decryption: To fully decrypt SMB3 traffic, both the session key and Session ID are required. The session key is not typically found in a PCAP and often necessitates memory analysis or cracking the hash with tools like Hashcat to derive the plaintext password and subsequently calculate the random session key.
  • •
    SMB Print Enumeration: For detecting SMB print enumeration activities, it is crucial to examine the Windows Security Log (Security.evtx) rather than Sysmon logs. Sysmon does not natively record these specific Windows object access events, making the Security Log the primary source for such artifacts.
  • •
    Event Viewer Prioritization: When conducting log analysis, prioritize using the native Windows Event Viewer for initial investigation. It provides a user-friendly interface for filtering and reviewing events. PowerShell cmdlets like Get-WinEvent should be used as a backup or for more complex, programmatic filtering and automation, especially when dealing with large datasets or specific XPath queries.
  • •
    Understanding Access Masks: An Access Mask (e.g., 0x12019F) is a hexadecimal code that precisely represents the permissions a user or process requests on an object. In incident response, analyzing this mask in logs (like Event ID 5145) helps determine the exact level of control an attacker attempted to gain over resources, such as the spoolss pipe.
  • •
    Security Logs vs. Sysmon for Object Access: While Sysmon is excellent for tracking behavioral activities like process execution and network connections, it does not audit Windows object permissions or network share interactions. For scenarios involving remote interaction with named pipes (e.g., \pipe\spoolss), the built-in Security.evtx log (specifically Event ID 5145: Network Share Object Access) is essential for capturing authorization artifacts like ShareName, RelativeTargetName, and AccessMask.
