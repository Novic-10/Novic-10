Executive Summary & Overview

A recently formed Australian company, transitioning to cloud infrastructure, experienced a significant security incident due to several misconfigurations. A group of attackers successfully leveraged these vulnerabilities to gain unauthorized access to their AWS environment. Lacking an in-house Incident Response (IR) team for cloud investigations and managing their cloud solely via the browser (no CLI configured), the company required external assistance to understand the scope of the breach and remediate the issues.

This writeup details the investigation into the compromise, tracing the attacker's steps from initial access through persistence and lateral movement. Key systems involved include exposed S3 buckets, compromised EC2 instances, and manipulated IAM identities. The investigation relies heavily on analyzing CloudTrail and VPC Flow logs to reconstruct the attack timeline and identify indicators of compromise.

Question & Answer Solutions

Let's walk through each investigation question in order, tracing how each artifact and memory or log clue points to the answer.

1. Which S3 bucket's object was accessed by the attacker?

developers-configuration

Reasoning: By filtering CloudTrail logs for eventName=GetObject and the attacker's source IP, we can extract the bucketName from the raw event data. The query used was index=* "bucketName" eventName=GetObject sourceIPAddress="18.216.138.52"| rex field=_raw "\"bucketName\":\"(?<Extracted_Bucket>[^\"]+)\""| table _time, sourceIPAddress, eventName, Extracted_Bucket.

2. What was the attacker IP associated in S3 access? (Provide the defanged IP)

18[.]216[.]138[.]52

Reasoning: The sourceIPAddress field in the CloudTrail logs for the GetObject event clearly shows the IP address 18.216.138.52. This was identified by parsing raw logs as key-value pairs were not consistently indexed. The query used was index=* "bucketName" eventName=GetObject sourceIPAddress="18.216.138.52".

3. What object/file did the attacker then access/download that would allow access to their environment?

VPN-Profiles/DevelopersProfile_wg0.conf

Reasoning: Further analysis of CloudTrail GetObject events from the attacker's IP revealed access to VPN-Profiles/DevelopersProfile_wg0.conf, a file type commonly used for VPN configurations, which could grant network access.

4. Based on the previous question, what is the software associated with the file? Provide the name of the software used for such type of files.

wireguard

Reasoning: The file extension .conf in conjunction with wg0 (a common interface name) strongly indicates a WireGuard VPN configuration file. This was confirmed through OSINT on the file type.

5. Using the previously mentioned file, one of the attackers accidentally connected via main system leading to his IP address getting leaked. What is the IP address of the Attacker? Provide the defanged IP

122[.]161[.]49[.]105

Reasoning: By analyzing VPC Flow logs for accepted connections (action=ACCEPT) to the WireGuard VPN port (dstport="51820"), the source IP address 122.161.49.105 was identified as the attacker's connection point. The query used was index=* sourcetype="VPC Flow" action=ACCEPT dstport="51820" | stats count by srcaddr.

6. What was the Private IP of the EC2 instance to which the attacker connected?

10.0.1.125

Reasoning: Reviewing VPC Flow logs and correlating with the attacker's connection activity, the destination IP address for the accepted VPN connections was found to be 10.0.1.125. Although some logs obscured the IP, cross-referencing with other flow records helped pinpoint the target instance. The query used was index=* "requestParameters.iPAddress"=HIDDEN_DUE_TO_SECURITY_REASONS (adjusted to find the actual IP in available logs).

7. The attacker performed further enumeration while being inside the EC2 instance and found a role that could be used further by assuming it. What was the ARN of the role?

arn:aws:iam::764581110688:role/ec2-role

Reasoning: Within CloudTrail logs, after the attacker gained access to the EC2 instance, events related to instance metadata or IAM role enumeration would reveal associated roles. The ARN arn:aws:iam::764581110688:role/ec2-role was identified as the role discovered by the attacker.

8. Using the role Attacker targeted IAM to achieve persistence in the environment. Provide the APIs used for it in order of its usage.

CreateUser, CreateAccessKey, AttachUserPolicy

Reasoning: Filtering CloudTrail logs for IAM events related to user creation and policy attachment, specifically excluding common read-only actions, revealed the sequence of API calls: CreateUser, followed by CreateAccessKey, and finally AttachUserPolicy. The query used was index=* sourcetype=cloudtrail "arn:aws:iam::764581110688:user/web_engg_1" eventName!="list*" eventName!="describe*" eventName!="Get*"| table eventTime, eventName, _raw| sort + eventTime.

9. Provide the name of the IAM Identity created during Persistence.

web_engg_2

Reasoning: The CreateUser API call in CloudTrail logs explicitly records the name of the new IAM user created. This was identified as web_engg_2.

10. What policy was attached to the Identity later? Provide the policy ARN.

arn:aws:iam::aws:policy/AdministratorAccess

Reasoning: Following the CreateUser and CreateAccessKey events, the AttachUserPolicy event in CloudTrail logs specifies the policy ARN attached to the new user. This was found to be arn:aws:iam::aws:policy/AdministratorAccess, indicating full administrative privileges.

11. Another EC2 instance was found to be accessed by the Attacker using SSH. Find its Private IP Address.

10.0.2.32

Reasoning: By examining VPC Flow logs for SSH connections (dstport=22) originating from the compromised environment or attacker IPs, a new internal destination IP 10.0.2.32 was identified, indicating lateral movement to another EC2 instance.

12. From the above EC2 instance, attacker then created a reverse shell. Find the Reverse Shell IP & port. Provide the Defanged IP

3[.]15[.]209[.]50, 13337

Reasoning: Outbound connections from the newly accessed EC2 instance (10.0.2.32) to unusual ports or external IPs in VPC Flow logs would indicate a reverse shell. The IP 3.15.209.50 and port 13337 were identified as the attacker's listener for the reverse shell.

Key Takeaways & Security Insights

  • •
    S3 Bucket Security: Misconfigured S3 buckets can lead to initial access by exposing sensitive data like VPN configurations and SSH keys. Implement strict access controls (least privilege), block public access by default, and regularly audit bucket policies.
  • •
    VPC Flow Log Monitoring: VPC Flow logs are crucial for detecting unauthorized network connections, including VPN access, SSH activity, and outbound reverse shells. Monitor for unusual source IPs, destination ports, and traffic patterns.
  • •
    IAM Role & User Management: Attackers will seek to establish persistence and escalate privileges. Regularly review IAM roles attached to EC2 instances and user permissions. Implement multi-factor authentication (MFA) for all users, especially those with administrative access, and monitor for CreateUser, CreateAccessKey, and AttachUserPolicy events in CloudTrail.
  • •
    SSH Key Management: Compromised SSH keys can grant direct access to compute instances. Implement strong key management practices, rotate keys regularly, and monitor CloudTrail for SendSSHPublicKey or similar events.
  • •
    CloudTrail for Audit & Forensics: CloudTrail is indispensable for auditing API activity and reconstructing attack timelines. Ensure it is enabled, configured for all regions, and logs are securely stored and monitored.
  • •
    Proactive Cloud Security Posture Management (CSPM): Regularly scan cloud environments for misconfigurations, exposed resources, and adherence to security best practices. This can prevent initial access vectors from being exploited.
